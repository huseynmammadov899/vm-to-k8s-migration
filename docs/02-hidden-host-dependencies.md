# 2. Hidden `/etc/hosts` dependencies

## Symptom

The pod starts and the health check is green, but the first real request fails:

```
java.net.UnknownHostException: legacy-db.corp.example
```

The same hostname resolves fine on the old VM.

## Root cause

Years ago someone added lines to the VM's `/etc/hosts`:

```
10.0.20.15   legacy-db.corp.example
10.0.30.7    partner-gateway
```

They were never in DNS. The app depended on them, but nobody had documented it, and a pod's
`/etc/hosts` is generated by the kubelet, so those lines simply don't exist there.

## Fix

**Short term: `hostAliases`** in the Deployment, see [`examples/k8s/deployment.yaml`](../examples/k8s/deployment.yaml):

```yaml
hostAliases:
  - ip: "10.0.20.15"
    hostnames: ["legacy-db.corp.example"]
```

**Long term: create real DNS records** and delete the `hostAliases`. Hard-coded IPs in manifests
break silently the next time a server moves.

## How I decided which entries to copy

A long-lived VM's `/etc/hosts` can have dozens of entries. Copying all of them carries the mess into Kubernetes.

1. Collect the non-default entries (the discovery script does this).
2. For each hostname, `grep -r` the application code and config. Keep only the names the app **actually uses**.
3. Check whether each name already resolves through cluster DNS:
   ```bash
   kubectl run dns-test --rm -it --image=busybox:1.36 --restart=Never -- nslookup legacy-db.corp.example
   ```
4. Add only the names that are used **and** don't resolve.

## Catch it earlier

Also watch for the same pattern in other places: `/etc/resolv.conf` search domains (short names
like `partner-gateway` resolve on the VM because of `search corp.example`), and NFS mounts in `/etc/fstab`.
